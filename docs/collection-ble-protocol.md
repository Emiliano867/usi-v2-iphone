# USI MPRLS BLE protocol, version 1

This is the binary contract between the private Feather ESP32-S3 sensor variant and the iPhone CoreBluetooth client. The committed vectors in `tests/fixtures/ble_*.hex` are synthetic software examples, not physical rate or delivery evidence. The host collection protocol remains version 2 and carries decoded samples, raw source identity, phone receipt time, and clock observations.

Service UUID: `0cda0100-6c5b-4a45-9a80-3e65c2316ab0`. The only notification characteristic is `0cda0101-6c5b-4a45-9a80-3e65c2316ab0`. The clock request write characteristic is `0cda0102-6c5b-4a45-9a80-3e65c2316ab0` and requires Write with Response. Legacy advertising includes the service UUID and short name `USI-BLE` (30 of 31 bytes including flags); the full GATT device name is `USI Pressure BLE`. Subscribe before treating the source as available. All logical message types share the one notification characteristic. A transport worker submits one whole logical message at a time to NimBLE’s host event loop, which serializes the final connection check and all notification calls with GAP lifecycle callbacks. Disconnect invalidates pending fragments and notification work from that connection; boot and source sequences continue until reboot.

All integers are little endian. Logical messages are 1…256 bytes. `boot_id` is nonzero uint32 and changes on reboot; pressure and trigger have independent uint32 raw sequences. The phone extends each sequence within its boot epoch. Device times are uint64 microseconds from the ESP timer. The first byte is message type:

| Type | Layout and fixed offsets | Length |
| --- | --- | --- |
| 1 PRESSURE | `type:u8@0, boot:u32@1, count:u8@5`, then 1…10 samples of `raw_sequence:u32, source_time_us:u64, p0/p1/p2:i32 centiPa, quality_error_mask:u8` (25 bytes each) | `6 + 25*count` |
| 2 TRIGGER | `type:u8@0, boot:u32@1, raw_sequence:u32@5, source_time_us:u64@9, pressed:u8@17, heartbeat:u8@18` | 19 |
| 3 CLOCK | `type:u8@0, boot:u32@1, request_id:u32@5`, then sixteen `u64` values at offsets 9,17,…,129 in the order below | 137 |

The production variant sends one pressure sample per logical message. Pressure p0/p1/p2 map to U3/ch0, U4/ch5, U5/ch6. Pressure is absolute Pa ×100; divide by 100,000 for kPa absolute. A failed sensor is exactly `-100` centiPa (−1.00 Pa), with its bit set in `quality_error_mask` (bit0=p0, bit1=p1, bit2=p2). The raw failure mask follows the legacy firmware. The v2 collection and seal models require **valid** bits, so `quality_mask=(~quality_error_mask)&7`; pressure quality alone does not imply calibration. Trigger `pressed` is the debounced active-low GPIO18 observation. `suction_on=!pressed` is derived, never motor feedback. `heartbeat=1` identifies a periodic current-state report; the BLE variant requests a 250 ms heartbeat and 25 ms debounce.

CLOCK's sixteen uint64 values are `t1_phone_ns, t2_device_us, t3_device_us, snapshot_device_us, pressure_acquired, trigger_acquired, pressure_overflow, trigger_overflow, pressure_disconnected, trigger_disconnected, scheduler_skips, pressure_notify_lost, trigger_notify_lost, notify_calls, notify_failures, disconnects`. The phone writes a 16-byte request `c7 01 04 00 | request_id:u32 | t1_phone_ns:u64`; firmware captures `t2` in the write callback and queues that request. The single acquisition owner inserts a clock barrier after earlier acquisitions, with `snapshot_device_us` and uint64 acquired counts at insertion. These acquired counts are the **next source sequences**, before modulo-2³² projection; they include samples rejected by queue overflow or disconnected transport. A full FIFO rejects the barrier, so the phone must time out its request instead of inventing a fence. The worker stamps `t3` immediately before fragmenting the clock response and copies its current notification rejection counters into the clock message. The phone captures `t4_phone_ns` on the first fragment's CoreBluetooth receive callback and records all four raw timestamps. Neither a clock observation nor a successful `notify()` call proves phone delivery; BLE fit validity and uncertainty are separate.

Pressure/trigger messages already admitted before the barrier are sent before CLOCK, and later admitted messages follow it. At the barrier, `pressure_acquired`/`trigger_acquired` define progress through source sequence `count-1`; the receiving phone must drain and verify those exact prior identities, allowing delayed fragments to complete, before submitting a final Stop fence. `overflow`, `disconnected`, `notify_lost`, `scheduler_skips`, and `disconnects` are cumulative per boot. Compare baseline and final deltas for a trial. `notify_lost` counts a whole logical sample lost after FIFO pop: a rejected fragment, an expired host event, or a connection generation rejection. `notify_calls` and `notify_failures` count actual fragment submission calls and their stack rejections. A host event waiting over 50 ms expires without being submitted; fixed contexts remain reserved until the host consumes expired events. `overflow` counts acquisition FIFO admission failures and `disconnected` counts samples produced or queued while unavailable. A successful stack admission is not delivery confirmation; received counts come only from decoded phone callbacks. No source progress is synthesized from a phone UI total. The sampled rate target of 6,944 µs (~144 Hz), BLE sustained throughput, and power/thermal behavior remain physical validation gates.

Each ATT notification is one fragment with a 10-byte header: `magic=0xc7:u8@0, version=1:u8@1, message_id:u32@2, total_logical_length:u16@6, offset:u16@8`, followed by 1…234 bytes. `message_id` increments modulo 2³² per logical message; offset begins at zero and must match the exact received byte count. The sender uses at most `min(negotiated_MTU-3,244)` bytes per notification. Default ATT MTU 23 therefore carries a safe 20-byte notification with 10 data bytes. Reassembly rejects duplicate, out-of-order, oversized, inconsistent, unknown-version, and malformed logical messages, abandons a partial after 500 ms, and resets on disconnect. A newer message can replace a partial message while accounting for the abandoned partial; the replacement ID must advance by less than half the uint32 range from the latest *started* message, even after an abort or timeout. A duplicate first fragment and backward or half-range replacement are errors. Maximum message length is 256 and maximum notification payload is 244.

For Task 4's iOS integration: discover the service with `centralManager(_:didDiscover:advertisementData:rssi:)`, `centralManager(_:didConnect:)`, `peripheral(_:didDiscoverServices:)`, and `peripheral(_:didDiscoverCharacteristicsFor:error:)`; call `setNotifyValue(true, for:)` on the notify characteristic and require `peripheral(_:didUpdateNotificationStateFor:error:)` success. In `peripheral(_:didUpdateValueFor:error:)`, capture monotonic phone time immediately, feed every `characteristic.value` notification to `USIBLEReassembler.feed(_:receivedNs:)`, and pass complete bytes to `USIBLECodec.decode(_:)`. On a CLOCK fragment with offset 0 and logical type byte 3, retain that callback time as t4 for its message ID. Build a request with `USIBLECodec.clockRequest(requestID:t1PhoneNs:)`, capture t1 just before `writeValue(_:for:type:.withResponse)`, and observe `peripheral(_:didWriteValueFor:error:)`; a write acknowledgment does not replace the clock response. On `centralManager(_:didDisconnectPeripheral:error:)`, reset the reassembler and connection ID, mark sensor freshness unknown, and resubscribe on reconnect. Keep decoded source acquired counts separate from received, forwarded, writer, reopened, and UI counts.
