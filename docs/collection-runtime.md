# Foundation phone collection runtime

`USICollectionRuntime` coordinates production collection packets on port 5559. It has no camera, Bluetooth, network, or UIKit dependency. The exact wire contract remains [collection-protocol-v2.md](collection-protocol-v2.md); host semantics remain [collection-host.md](collection-host.md). Native adapter compilation and physical validation are separate gates.

## Ownership and assembly

1. Create one dedicated serial `DispatchQueue`. Construct `USICollectionRuntime(sessionID:worldEpochID:ownerQueue:)` with that queue. Use a real new phone session ID on process/session restart and a new world epoch on tracking reset. All runtime methods and reads run on that queue; its preconditions enforce ownership when `ownerQueue` is provided. UIKit receives immutable rendering snapshots on main.
2. Use the same queue for `ARSession.delegateQueue`, CoreBluetooth's manager callbacks, the `NWConnection` queue, user-action admission, and periodic `tick(nowNs:)`. Acquire monotonic timestamps at the actual callback. No runtime method blocks for another owner, JPEG, a clock response, or a socket.
3. In the camera callback, preserve the native preview buffers separately, extract actual value-only `USICameraPose`, and synchronously call `admitCamera(pose:)` before starting JPEG. The runtime assigns the source sequence and immediately validates/queues the independent pose. The returned `USICameraAdmission` contains `posePacket` and an optional opaque `encodeTicket`. Do not enqueue `posePacket` a second time.
4. Start JPEG only for a returned ticket. Keep external encoder work bounded by the runtime's outstanding tickets. Return exactly once on the owner using `completeCamera(ticket:image:)`; `nil` means a real encode failure. Populate `USICameraImage` from actual calibration, JPEG bytes, and optional tightly packed raw depth/confidence; never substitute default matrices or pressures. An unavailable ticket needs no completion. `outstandingEncodeTickets` exposes the admitted identities; `encodingRecommended` becomes false during Stop/Finalizing/unknown or without a host. Acquisition and preview may continue. Pending pre-end tickets may still complete as drain tails.
5. A real independent ultrawide adapter may use `admitUltrawide(epochID:sourceTimestampS:sourceClock:phoneUptimeNs:)` followed by the same completion API. Capability probing, independent timestamps/intrinsics, and accurate unavailability reasons remain native responsibilities. Full cannot start without a real fresh ultrawide lane.
6. After a BLE boot identity is decoded, call `connectBLE(sourceID:bootID:connectionID:nowNs:)` for every connection. Retain the first observed logical message with its real first-fragment timestamp and admit it with `receiveBLE(_:firstReceivedNs:completedNs:)`. Bootstrap reassembly must itself be bounded and report aborted messages. Thereafter either keep one adapter-owned reassembler and use the logical API, or use `receiveBLEFragment(_:receivedNs:)`. The latter detects replacement/discard loss as well as malformed fragments. Do not run two reassemblers over the same notifications.
7. Drain `takeEffect()` after each owner event. For `.requestBLEClock(requestID:t1PhoneNs:)`, write exactly `USIBLECodec.clockRequest(requestID:t1PhoneNs:)` on the real BLE control characteristic. Pass the ordered, correlated response back through `receiveBLE`; never synthesize acquired counts. Pressure/trigger bootstrap buffers hold 128 samples each until that barrier seeds their independent uint64 identities. `requestBLEProgress(nowNs:)` optionally requests another bounded observation; false means busy/unavailable. Begin/Stop defer behind a pending periodic observation and then request their own fresh boundary observation while gates stay closed.
8. On a host connection call `connectHost(capabilities:nowNs:)`. It queues HELLO and HEALTH and, if unresolved, a status query for the same trial. Decode inbound strict v2 packets and call `receiveHost(_:receivedNs:)`. Handle PING with `replyToPing(_:receivedNs:sentNs:)`, using actual receive and response-construction times. Completed USB clock observations are retained without echo.
9. The socket writer calls `takeNext()` only when it can start one whole wire packet. Send `send.packet.bytes` as one ordered byte sequence. Call `sendCompleted(token:succeeded:)` exactly once on owner, then pump again. The runtime refuses a second in-flight packet; old completion tokens cannot complete a replacement send. Do not split packets across independent writers. This bounds application admission; it makes no physical-delivery or socket-latency claim.
10. `.disconnectTransport(reason:)` means close the actual host connection once and show the local unresolved reason. Also report real network/BLE errors through `disconnectHost(reason:)` / `disconnectBLE(reason:)`; call `background()` and `resetWorld(epochID:)` for those events. Reconnection never resumes a hidden recording. A periodic owner timer must call `tick(nowNs:)` to enforce clock deadlines, source stale grace, and bounded command retries.

## Trial and queue behavior

Live data flows before Prepare. Build a `USICollectionSnapshot` from actual inventory, explicitly selected Core/Full, task/gripper settings, and optional validated pressure calibration. `readiness(snapshot:nowNs:)` checks required raw lanes, capability availability, host freshness/readiness, and synchronized BLE progress. Suction and seal colors are independent of readiness; calibration may be nil.

`prepare(snapshot:trialID:requestID:nowNs:)` freezes that snapshot. A correlated host Preparing acknowledgment closes forwarding, snapshots the next camera acquisition identities, and starts an ordered BLE barrier. Held ingress stays bounded. At completion, records below the Begin fences are discarded; HEALTH baseline and Begin are queued ahead of post-Begin data. Recording assurance starts only on a correlated fresh host Recording status, with one elapsed-time anchor per trial.

`stop(requestID:nowNs:)` closes forwarding immediately, snapshots camera ends, then obtains the actual BLE end counts. Stop is queued before retained `< end` tails. Newly acquired camera/pose/sensor records at or above end remain suppressed until a terminal host outcome. A stale/unavailable BLE source, failed barrier, or Stop before acknowledged Recording cannot produce valid complete fences: the runtime emits one disconnect effect and retains a frozen unknown outcome. Stop stays reachable. Reconnect queries the same trial, and a recovered Finalizing status keeps forwarding closed. Only authoritative terminal resolution unlocks configuration. Saved needs strict Passed/path metadata and must not conflict with measured local trial loss.

The queues reject newest rather than replace samples. Defaults are 4 image packets, 128 pose packets, 128 sensor packets, 32 control packets, and 20,000,000 bytes per lane, plus at most one in-flight wire packet. The encoder admits at most 4 outstanding tickets. Control has priority; pose/sensor/image scheduling rotates fairly. Runtime-generated data packets contain one source record, so boundary filtering never silently removes half a batch. All packet builders use `USICollectionWire` validation.

Request bytes and expected revisions remain stable on retry. The request ledger has 4096 entries and refuses exhaustion; each request has at most three sends. Only read-only status retries are allowed while local outcome is unknown.

## Counters and rendering

`counters` and each rendering stream's `phone` counters are observed epoch-cumulative local totals; BLE `sourceCount` is the actual latest ordered source progress observation. Phone received counts remain separate from source acquired counts. `beginCounterSnapshot` / `endCounterSnapshot` preserve the actual boundary snapshots, independent of later live acquisition. Writer counts are null on the phone. Camera source-prefix rejected/overflow totals are null at a boundary when older outstanding encoder tickets can still fail or overflow later. Null does not erase known loss.

`lossTotals` and rendering stream `losses` distinguish encoder ingress overflow, encode failure, malformed source rejection, and transport overflow. FRAME `encode_drops` includes ingress/encode/source rejection; `transport_drops` counts transport overflow. These FRAME totals remain honest epoch-cumulative values. `trialLossCounters` / stream `trialLosses` retain observed in-interval losses. The runtime retains full `latestBLESourceProgress` provenance, including boot/connection, first receipt/completion times and every original CLOCK progress/loss category. Its HEALTH sensor overflow total aggregates source overflow, disconnected acquisition, notify loss, pressure scheduler skips, and phone queue loss, with checked arithmetic.

`render(nowNs:)` supplies sector-mapped states/numeric kPa absolute, independent trigger-derived suction, host assurance, timer, frozen/Stop flags, latest save, separate required-missing/profile-excluded inventories, and all stream rows. Rate inputs are individually nullable (`selectedSourceFPS`, acquisition, preview, encode, host receive, host write); adapters provide real measured values through `setRates`. Opening diagnostics must only render these inputs, never replace capture ownership.

## Required host integration repair

The current host compares FRAME lifetime drop counters against its latest warm FRAME before checking that frame's trial fence (`collector.py`, `_begin_frame_counters` / FRAME ingest). Reproduction: admit an image before Begin, leave its ticket outstanding across Begin, fail that encode after Begin, then encode a valid in-trial image. The valid image truthfully carries an increased lifetime `encode_drops`; the host can label this trial Incomplete even though the failed image was below Begin. Similarly, an out-of-fence encode admitted before Stop integration is quiesced can increase a later valid tail's lifetime counters. Unknown source-prefix baselines require the same care. These are conservative false-Incomplete risks; no counters are relabeled to hide them. Integration must reconcile loss evidence against acquisition identities/prefix availability before delivery. This Foundation task does not change host accounting or claim that gate passed.
